# SHA-256 r39 packed birthday walk: the 32-byte message edition

Source: `research/checks_1015/pa_src/pos_s256r39/experiments/shrho.py`

Public SHA-256: `ddce56a9568dec4301801baa8bc63c51efecfaeba188cc2ef9f33aac80289f1b`

## Reviewed usage contract

This archived program walks the 256-bit feed-forward digest of 39-step SHA-256 with the standard IV. Each point encodes a 32-byte one-block message. It packs seven 32-bit arithmetic lanes, with four guard bits per lane, into each 256-bit machine word. This is generic birthday search machinery, not the row-16 differential claw construction and not a new all-round SHA-256 break.

## Source inspection and available execution evidence

static-source-review; Fixed independent digest fixtures, Python kernel/allocation controls, synthetic helpers, explicit-Tp ledger and empty CLI only; no search or sampler.

The publication checker gives each finite CLI child a 15-second timeout. This is a test guard, not a runtime promise. Nonempty experiment requests, --selftest and --stats are not bounded website examples. The historical reference divisor of 2812 belongs to the declared word-operation model, not CPU seconds.

## Declared inputs

**Message layout**: W0..W7 are the variable 32-byte message; W8 is 0x80000000, W9..W14 are zero and W15 is 0x100. The scalar and packed functions use the same big-endian digest-to-next-input convention.

**Exact edition**: Download this record and check its SHA-256. The two similarly named shrho.py archives implement different message families; do not exchange their generated code, ledgers or known answers.

**Search-free CLI**: --gen-c prints embedded C source without compiling or running it. JSON stdin with experiment_id=proj-k0-w256 and trials=[] checks the empty serializer. An empty shrho-n18 request also constructs the Python kernel, but runs no search.

**Experiment modes**: shrho-n18 runs reduced-width 18-bit searches and a keyed-control diagnostic. proj-k0-w256 evaluates full-width hashes but looks for equality in only a 16-bit projection. Nonempty trials require seed and trial; these are research computations, not the guide smoke test.

**Planning versus running**: --ledger, --loss and --sweep compute declared models. The default planner scans Tp=1..8192 using floating-point tail calculations. --selftest includes real reduced-width searches, and --stats defaults to 256 experiment repetitions; neither was run by this publication check.

## Outputs and interpretation

**Finite independent digest check**: 28 fixed 32-byte messages agree at 39 steps with the separate indep_sha256_check.py implementation, after three fixed full-64-step checks against hashlib. The generated and allocated kernels agree with those 28 outputs across four seven-lane batches. These are arithmetic fixtures, not sampled success rates.

**Generated code model**: The pinned edition emits 2,426 primitive instruction records. The source allocator uses 43 registers; its peak-live model reports 39. Python straight-line and allocated execution were checked. The C/WASM backend and complete-machine charge were not certified.

**Exact integer ledger, conditional interpretation**: A fixed Tp=1 control reproduces all seven ledger components and both memory-phase totals using integer arithmetic. It is deliberately not the optimized default plan or a new contest price. The probability model, generator constants and memory/primitive conventions remain separate obligations.

**Projection event**: dup_* is len(values)-len(set(values)), the number of repeated entries beyond the first of each value. It is not the number of unordered equal pairs: three equal entries contribute 2 duplicates but 3 pairs. The publication reproduced that distinction with a mocked seven-value interface, not a real hash experiment.

**Bit positions**: The projection named p23 concatenates eight bits at offset 64 and eight at offset 107. Read these offsets from the implementation; do not assume two conventional adjacent word boundaries.

**Witness scope**: JSON message_a_hex and message_b_hex can describe a reduced event. An 18-bit walk or 16-bit projection match is not a 256-bit collision, even though the underlying digest routine executes all 39 specified steps.

## Failure modes

- There is no --help parser. Unknown command-line arguments fall through to JSON stdin; an interactive process can wait for input.
- Unknown experiment IDs raise ValueError and missing trials raises KeyError; the interface is not a complete request validator.
- pack_lanes says up to seven values but does not enforce the count. Eight all-one inputs produce integers wider than 256 bits. Callers must validate lane count.
- pack_entry asserts only upper bounds, so negative fields can pass and corrupt packing. Supply nonnegative 64-bit key, 16-bit trail index and 120-bit length; the three valid boundary round trips and three upper rejection controls were checked.
- Do not call loss(plan(18)): reduced plans set cmax=1000000000 and loss constructs a list over range(cmax+1). The publication checked the value without allocating the list. CLI --loss uses the full-width plan instead.
- phase_bytes uses the global 64-register REGFILE. If reviewing a 32- or 16-register alternative, reconcile that footprint with the R-specific machine_constants result rather than silently treating them as the same formula.
- The keyed first-repeat experiment changes the family and the BLAKE2b control is a concrete keyed function, not a proof of ideal random mapping. Neither alone establishes the success law for the fixed 256-bit target.
- The declared instruction size, generator allowance, cutoff/tail losses and reference compression price are modeling premises. Exact arithmetic replay does not turn them into proved physical runtime or unconditional attack success.
- Do not use python -O for evidence: assertions disappear. Preserve the source credit to the earlier BLAKE3 distinguished-point and packed-lane work.
