# BLAKE3 B4F: smaller stored code, more recovery operations

Source: `research/blake3_r4/b4f/pkg/blake3/experiments/bsrho.py`

Public SHA-256: `0d25cea3ac5bf0cff088b7b89e0e0e71a07b14a5bb3521905691f4ddfe149182`

## Reviewed usage contract

B4F makes a concrete code-space/work tradeoff: store one recovery-round body and execute it four times, then use shorter endpoint records. It also replaces the probability helper with a binned detection-delay calculation. Those are distinct changes. This guide shows the implementation evidence without treating a smaller program or a numerical model output as a new attack proof. The original source retains its predecessor and jungjipdo attributions.

## Source inspection and available execution evidence

static-source-review; Own-pin arithmetic/allocation, independent rolled-instruction interpreter, finite synthetic recovery, fixed-plan ledger and two numerical grids. No default optimization or original collision attempt..

One finite main-circuit construction/allocation and one rolled recovery construction, tested with a ten-second subprocess limit. No default numerical optimization or original collision campaign.

## Declared inputs

**Same hash target**: Four-round BLAKE3 on the full block 32 zero bytes followed by little-endian x, standard IV, counter 0, length 64, flags 11 and unit 846. The stored walk is f XOR q. The main bit-sliced batch remains 24,422 instructions and allocates 771 registers.

**Rolled packed recovery**: Each 256-bit register holds seven 36-bit lanes: 32 data bits and four guards. Recovery uses 35 register slots. The stored blocks contain 24 loads, a 248-instruction round body, 18 message-slot moves and 16 output instructions, plus five control instructions. Masking restores clean state words at each round boundary.

**Seven-byte endpoint layout**: A record contains a 40-bit key and a 16-bit trail ID. The table capacity is rounded down to a multiple of 32 records. This is not the earlier 64-bit-key layout: a repeated truncated key still needs full recovery and equality checking.

**Numerical-helper inputs**: The helper fixes the full-width model and exposes fine/coarse bin counts. Supply positive integers. A zero coarse count raises division by zero; zero or negative fine counts are accepted but omit the final bins and can understate the delay loss. No default impact is inferred. The run-length cache still omits Sb, so use a fresh process or clear it when changing that parameter.

**Finite entry point**: The example builds both circuits and prints the main allocation and the recovery execution/storage counts. It does not launch --selftest, --stats, a default plan, a collision attempt or an embedded-C build. B4F changes the generator’s CODE_BYTES constant, so no earlier retained-wasm result is transferred.

## Outputs and interpretation

**Stored code versus executed work**: Recovery stores 311 instructions but executes 1,102 primitive operations. Stored: 24+1+248+3+18+1+16. Executed: 24+1+4(248+3)+3(18+1)+16. With the source’s extra 64 operations, each recovery batch is charged at 1,166, not 900 as in the earlier straight-line edition.

**Independent finite interpreter**: A separate interpreter truncates every instruction to 256 bits. It matches 36 seven-lane fixtures (252 values), all lane counts from zero through seven, clean round boundaries and the exact message permutation; an output-mask mutation is rejected. Fresh independent digest/allocation controls also pass. These are finite fixtures, not a universal proof of every packed-input guard bound.

**Declared layout arithmetic**: Body=24,459, code=935,172 bytes, table=10,176 seven-byte records. Declared setup/search phases are 1,023,204 and 1,048,388 bytes. The code shrinks by 18,900 bytes relative to the 836-instruction recovery, while the table also benefits from shorter records. This is source-model accounting, not native memory measurement or a full handler audit.

**Exact saved-plan ledger**: At supplied historical Tp=144 and B=1360395196615000000000000000000000000, every integer ledger part is recounted. N=34393264232537607816282550281404880802960 word operations, with decimal log2(N/846)=124.934735989574228827915567797523765562377622954270808853739. This reproduces arithmetic behind 124.93474; it is not a new accepted or premise-free score.

**Fixed-grid diagnostics**: At those parameters, fine/coarse grids 20,000/2,000 and 40,000/4,000 return P_lower=0.3900000010005341 and 0.3900077577177947. The refined grid decreases the computed delay term. Agreement or monotonicity at two grids is not a convergence certificate, a complete rounding proof or validation of the random-function/target-transfer premise.

**Synthetic interface controls**: Four field roundtrips and two upper-overflow rejections pass; negative -1 aliases unsigned maximal fields. Six one-batch constant-map cases cover a returned artificial pair, a miss and four budget exits. Four finite recovery graphs require 5, 7, 4 and 2 calls. These controls preserve the common-endpoint premise and are not real BLAKE3 witnesses.

## Failure modes

- Do not use 311 as the per-call recovery operation count; it is stored code size.
- Do not reuse the predecessor’s 64-bit key, 10-byte record or 836-operation recovery charge.
- Validate positive integer numerical grid counts; nonpositive fine counts silently omit bins.
- Do not carry B4E’s trapezoid certificate into the different B4F delay model.
- A shared-endpoint premise and final equality check remain necessary after a truncated-key match.
- Finite interpreter fixtures and two numerical grids do not certify the entire machine or attack-success law.
