# Poseidon recorded pairs: replay the r3–r5 witnesses

Source: `research/poseidon/pkg_r7_paper/out_draft/experiments/replay_pairs.py`

Public SHA-256: `497ce3f69860a10e518908f46163bb984cd9ed20ce7c184004fb236e3bd65b1c`

## Reviewed usage contract

Replay one recorded Orchard Poseidon collision at each of r=3,4,5 partial rounds, plus eight fixed full rounds. Rebuild canonical 64-byte messages and compare both complete digests with the recorded digest. These existing library witnesses provide auxiliary evidence for a higher-round package; its selected target needs a witness at that target.

## Source inspection and available execution evidence

static-source-review; copied CLI, three independent digest/identity comparisons and negative controls; no discovery search.

One request performs six fixed digest evaluations, independent of the number of requested output rows: 72 MDS layers and 168 fifth powers across the r3,r4,r5 pairs. JSON parsing, encoding, comparisons and serialization add work. This is a small finite replay, not the cost of discovering these pairs or a higher-round collision-search charge.

## Declared inputs

**JSON request**: trials is a list of objects with caller trial identifiers. Other request metadata and seeds are ignored, including schema_version, target_profile and event. The replay uses the embedded PAIRS table, not supplied messages. An empty list still runs the three replays; a missing trials key fails after replay.

**Exact parameters and encoding**: P is the Pallas field, capacity is 2^65, and each message is nk followed by rho, each as a canonical 32-byte little-endian field element. Each digest uses original constant rows 0..3, then 4..(3+r), then 60..63; r counts partial rounds. The MDS and retained constant rows match the library’s independent finite-replay bundle.

**Unconditional entry point**: The source ends with main() without a name guard. Importing it or using runpy executes the replay and reads stdin. Use the documented subprocess JSON example instead of importing the unmodified file.

## Outputs and interpretation

**Repeated replay observations**: Each response row preserves its trial identifier and returns message_a_hex=null and message_b_hex=null. The fixed observations are replay_pairs_checked=3, replay_pairs_ok=3 and replay_all_ok=1 for this unmodified source. Multiple response rows repeat the same result; they do not represent new sampled pairs.

**Three existing identities**: The numerical messages and target profiles match w-4e56e673baa1bc55 (r3), w-edf7ea8e3a6b84b3 (r4) and w-ff1c8d46105889fb (r5) in data/finite-witnesses.json. All six digest computations agree with the independent checker, and a fixed one-bit change is rejected for each profile. No new discovery is counted.

**Failure is a verdict, not necessarily a process error**: A bad recorded digest, identical messages, noncanonical input or changed message makes replay_pairs_ok smaller and replay_all_ok=0. main still emits a normal response; do not infer success from exit code alone. An empty embedded pair table gives replay_all_ok=0 rather than a vacuous pass.

**Round boundary**: The comment reserves space for a future r6 pair, but the actual PAIRS table has only r3,r4,r5. The retained round-constant dictionary supports the needed low-round evaluations; calling digest at r7 fails on missing row 10. Neither that comment nor the file’s placement in an r7 package proves an r6 or r7 collision.

## Failure modes

- The response deliberately has no message pair for the selected higher-round target. Its auxiliary observations cannot be treated as a successful organizer collision trial.
- Read replay_all_ok and the checked count. A normally terminating process can report a failed replay.
- The r6 placeholder comment is not evidence that an r6 pair was recorded; no such tuple exists in this edition.
- Request metadata and seeds are ignored. Repeating trial identifiers or changing seeds does not change the embedded witness table.
- The scalar digest helper reduces its inputs during arithmetic; canonicality is checked separately by replay. Do not substitute the helper alone for a canonical-message verifier.
- A finite witness replay validates those message/profile identities, not historical work, discovery probability, priority or current judge acceptance.
