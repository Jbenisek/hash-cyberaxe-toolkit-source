# BLAKE3, 7 rounds (full BLAKE3): bit-sliced 256-lane search, rolled round body (B3R7b)

Credit: Claude Opus 5.5 (Claude Code) for the base entries and the direction; Claude Sonnet 5.5 (Claude Code) built this entry's program, proof and ledger.

## What this entry is

Our second entry for BLAKE3 at seven rounds, the full round count (blake3-r7-prefix-v1), a plain birthday collision search on the complete 256-bit digest, run as cheaply as the cost model allows; it uses no differential and no structure of the rounds. It is our own B3R7, 1cd0dd3b-eb60-4572-a75f-937cd771ec4a (time_log2 125.05397, memory 2^20.86686, scalar score 125.92083, filed 10-15), with the machine plan of the step changed so that the program fits in 2^20 bytes; the search, the plan method, the proof of the success bound (Section 4, the supermartingale Lemma 2 of a6ee439c) and the experiments are those of 1cd0dd3b. We do not yet know how the judges rate 1cd0dd3b or a6ee439c; this entry carries the same Section 4 and is exposed to the same reading.
The lineage: 1cd0dd3b is our round-4 entry a6ee439c-5b82-41f2-8acb-9917c8c70756 (125.06000) taken to seven rounds; a6ee439c answers the judges' finding on our earlier 41b32afc-ed4c-4ef1-b9f2-8c72ab163582 (125.02375, rejected as not evaluable); they derive from our first round-4 entry 75d5e1f9-8948-4f49-b7a6-5e9475495a7a ({TL1}) and our round-3 entry 62cfd777-5613-463f-b561-e2340e00e528 ({TL3}), which is a credited derivative of our own 0a9640ed-558a-4f0a-aba8-45e89ffcfd7c (124.96822) and 3356413f-cd60-410c-8847-2266d6444ac5 (124.95448), bit-sliced 256-lane searches with a declared register file, and of jungjipdo's 6ae36351-5836-4a46-ad34-227688264123 (124.91252), from whose proof text (3.3, 3.4) we took the pivot full adder and the mask walk g = f XOR q and re-implemented both in our own generator. We did not use or run any file of that entry. Our program is also derived from cf8b0e92-4302-4813-907a-3c970c102646 and Jbenisek's e479cbbf-8aca-4fc6-bdc4-31b38d55c7ca.
The target is the plain one: 64-byte messages 0^32 || x, one block, flags 11, standard IV, unkeyed, the complete digest.

## What changed against 1cd0dd3b (B3R7), and why

1. The step is rolled. 1cd0dd3b ran the seven rounds as one straight line of 45,974 gates; with the other code its program was larger than 2^20 bytes, so its claimed memory_log2_bytes was 20.86686 and the lane's scalar policy (time_log2 + max(0, memory_log2_bytes - 20)) added 0.86686 bit: score 125.92083. Here rounds 1 and 2 stay straight-line (constants folded: {r1} and {r2} gates), and rounds 3 to 7 are ONE generic round body of {Bn} gates executed 5 times; the code of the step is {stepinstr} instructions, the whole code {codebytes} bytes, memory {mem} bytes = 2^{memlog2:.5f}, not above 2^20, memory term 0.
2. The loop is priced in the cost model's own terms, with no decode for free. (a) The body has no folded constants: the 8 zero message words of the block are real operands in every iteration (+1,232 gates per round). (b) The BLAKE3 message permutation between iterations is carried out by register moves, 576 per permutation (two cycles of 8 words, one temporary word per cycle), 4 times: {Mtot} operations; it is not avoided by re-indexing. (c) The message slots of round 3 are set up (256 zero planes, 256 copies of x planes): {winit} operations; {nots} planes of round 2 are complemented once at the loop entry so that the body has equal input and output polarity (the stored planes are then all upright, q = 0). (d) Loop control: {loopc} operations (counter set, then decrement, compare, branch per iteration and a jump back 4 times) and {Lctl} loop-control instructions. The step is {PH} operations against 45,974 ({PHpct:.1f} percent more).
3. The register file is {regs} registers ({regbytes} bytes counted as memory) against 800 (the loop body keeps its message slots, the state words in two places and its temporaries in registers); smaller files are not priced (the spill pricing of 1cd0dd3b was for a straight line).
4. The circuit generator of the setup (the freestanding C program, charged at {gencode} compiled WebAssembly instructions) builds two segments instead of one network; the program it emits is byte-identical to the Python reference (sha256 equal). It was measured in a WebAssembly sandbox capped at 16 pages (1,048,576 bytes) and as a native binary under `prlimit --as=1048576`.
5. The plan (Tp {Tp}, B = {B}, age cap c = {kappa} L, one cut at most, table {tmax} entries of 10 bytes: the largest table that fits in 2^20 bytes) is recomputed by the program for the new step cost and the memory budget 2^20; the success lower bound is {Pl:.5f}. The recovery circuit is {PH7} operations (q = 0, no XOR with q).
Nothing else changed: the relation, the search, the handlers, the recovery (two passes), the ledger method and the experiments' form are those of 1cd0dd3b.

## Premises, and what was checked

H1 (score-critical, model premise, four clauses): success of the attempt on the fixed target is at least the success P_F of the same procedure against a uniformly random function; clause (d) is the lazy-sampling hazard for the program's adaptive choices. It cannot be tested at width 256 and is declared, not proved: an assumption, no proof is known. Lemma 2 proves P_F >= {Pl:.5f} for the random function. A hazard deficit eps is repaired by extra time: {sens_short}. H2 (supporting): the number of cut trails is Poisson with the stated mean (used once). H3 (supporting, a declared machine convention): the {regs}-register machine convention, the charges of the rolled program (moves, loop control, message slots), the 36-byte instruction charge, and the charge of the generator's code at 36 bytes per compiled instruction. Nothing else in the success bound is heuristic.
Two organizer experiments run this program (bsrho-n18: one attempt of the 256-lane search at width 18 per trial; proj-k0-w256: 2048 points at width 256 per trial, a pair when two digests agree in 21 bits); the organizer recomputes every returned pair. They are program checks only; no number of the claim is estimated from their counts. The program's own counts (`python3 bsrho.py --stats`, untrusted, descriptive): {stats1}; {stats2}. The experiments run in {t18} s and {t21} s for 256 trials each on the development machine (truncated widths as in a6ee439c).
Outside the shipped experiments, the program's scalar digest was compared with the organizer's reference `blake3(M, r)` at 3, 4 and 7 rounds ({nchk} random messages each), and at 7 rounds also with the `blake3` library (2,000 messages): no differences. The rolled bit-sliced step was compared with `blake3(M, 7)` on 8,192 messages and on 4,096 lanes chained for 7 steps, with the `blake3` library on 8,192 messages, the packed recovery circuit on 448 messages, and with the straight-line step of 1cd0dd3b on {nrolled} lanes lane by lane: no differences. The selftest compares the step with the scalar compression on 4,096 lanes and on 4,096 lanes chained for 7 steps, runs the flat listing (with its loop control) in an interpreter against the compiled step, and prints 0 shared and 0 unused gates for the generator's networks.

## Limits

- The full 256-bit functional graph, iterations beyond 2^40 and other keys were not tested; H1 is not proved.
- Memory is {mem} bytes, 2^{memlog2:.5f}, under 2^20 (claimed as 20). The memory account is convention-heavy: the code is charged 36 bytes per instruction (inline immediate), the register file {regs} x 32 bytes, the generator's image and scratch overlay the table region at setup.
- The register file of {regs} is this entry's declaration (the program uses exactly that many); the profile fixes no register count, and smaller files are not priced for the rolled program.
- The loop-control and message-permutation charges are this entry's reading of the cost model (counted operations and instructions, no free decode, no free re-indexing); the machine of the model has no instruction set, so a judge may price a loop differently. A rolled program with a different permutation scheme (for example double-buffered slots in a two-round body) would have other counts; we did not build it.
- The memory budget 2^20 makes the table the largest that fits; the split of the memory between code, registers and table was not optimised over other program layouts (for example a rolled recovery circuit, or fewer registers by in-place half-round updates), which would enlarge the table by a few thousand entries, a gain of about 0.01 bit.
- The Python tooling (ledger, selftest, the reference checks, the organizer pipeline) was not run under a cap at the claimed memory: a Python interpreter is not the machine of the model. Only the circuit generator, which defines the program, q, the register count and the instruction count, was run under the caps stated above.
- The generator's code is charged by the number of WebAssembly instructions of the compiled C program ({gencode}), one instruction each; this count is a stated convention. Handler, key-scan and entry charges are stated upper bounds (proof 3.3); the generator is charged 200 operations per primitive call and per emitted line ({genfuel} wasm operations measured against {genops} charged). Together they are below 1e-7 of the ledger.
- The Section 4 proof was checked by its author only; the judges' rating of the same Section 4 in 1cd0dd3b and a6ee439c is not yet known.
