## What this entry is

Our entry for BLAKE3 at seven rounds, the full round count (blake3-r7-prefix-v1), a plain birthday collision search on the complete 256-bit digest, run as cheaply as the cost model allows; it uses no differential and no structure of the rounds. It is our own B3R7c, a2e94df7-bff4-4461-ad40-7f75930cb241 (time_log2 125.29113), with the proof of the success bound (Section 4) rewritten as a first-collision proof and B and Tp re-planned; the target, the rolled step, the search, the recovery, the ledger and the experiments are those of a2e94df7. Its lineage starts at our B3R7, 1cd0dd3b-eb60-4572-a75f-937cd771ec4a (time_log2 125.05397, memory 2^20.86686, scalar score 125.92083), whose machine plan of the step was changed so that the program fits in 2^20 bytes.
The lineage continued: 1cd0dd3b is our round-4 entry a6ee439c-5b82-41f2-8acb-9917c8c70756 (125.06000) taken to seven rounds; a6ee439c answers the judges' finding on our earlier 41b32afc-ed4c-4ef1-b9f2-8c72ab163582 (125.02375, rejected as not evaluable); they derive from our first round-4 entry 75d5e1f9-8948-4f49-b7a6-5e9475495a7a (125.35348) and our round-3 entry 62cfd777-5613-463f-b561-e2340e00e528 (124.8123), which is a credited derivative of our own 0a9640ed-558a-4f0a-aba8-45e89ffcfd7c (124.96822) and 3356413f-cd60-410c-8847-2266d6444ac5 (124.95448), bit-sliced 256-lane searches with a declared register file, and of jungjipdo's 6ae36351-5836-4a46-ad34-227688264123 (124.91252), from whose proof text (3.3, 3.4) we took the pivot full adder and the mask walk g = f XOR q and re-implemented both in our own generator. We did not use or run any file of that entry. Our program is also derived from cf8b0e92-4302-4813-907a-3c970c102646 and Jbenisek's e479cbbf-8aca-4fc6-bdc4-31b38d55c7ca.
The target is the plain one: 64-byte messages 0^32 || x, one block, flags 11, standard IV, unkeyed, the complete digest.

## What changed against 1cd0dd3b (B3R7), and why

1. The step is rolled. 1cd0dd3b ran the seven rounds as one straight line of 45,974 gates; with the other code its program was larger than 2^20 bytes, so its claimed memory_log2_bytes was 20.86686 and the lane's scalar policy (time_log2 + max(0, memory_log2_bytes - 20)) added 0.86686 bit: score 125.92083. Here rounds 1 and 2 stay straight-line (constants folded: 2,614 and 7,184 gates), and rounds 3 to 7 are ONE generic round body of 8,416 gates executed 5 times; the code of the step is 19,803 instructions, the whole code 812,844 bytes, memory 1,048,510 bytes = 2^19.99991, not above 2^20, memory term 0.
2. The loop is priced in the cost model's own terms, with no decode for free. (a) The body has no folded constants: the 8 zero message words of the block are real operands in every iteration (+1,232 gates per round). (b) The BLAKE3 message permutation between iterations is carried out by register moves, 576 per permutation (two cycles of 8 words, one temporary word per cycle), 4 times: 2,304 operations; it is not avoided by re-indexing. (c) The message slots of round 3 are set up (256 zero planes, 256 copies of x planes): 512 operations; 240 planes of round 2 are complemented once at the loop entry so that the body has equal input and output polarity (the stored planes are then all upright, q = 0). (d) Loop control: 20 operations (counter set, then decrement, compare, branch per iteration and a jump back 4 times) and 5 loop-control instructions. The step is 55,210 operations against 45,974 (20.1 percent more).
3. The register file is 1856 registers (59,392 bytes counted as memory) against 800 (the loop body keeps its message slots, the state words in two places and its temporaries in registers); smaller files are not priced (the spill pricing of 1cd0dd3b was for a straight line).
4. The circuit generator of the setup (the freestanding C program, charged at 2,249 compiled WebAssembly instructions) builds two segments instead of one network; the program it emits is byte-identical to the Python reference (sha256 equal). It was measured in a WebAssembly sandbox capped at 16 pages (1,048,576 bytes) and as a native binary under `prlimit --as=1048576`.
5. The plan (Tp 232, B = 1345366764123000000000000000000000000, age cap c = 14 L, one cut at most, table 15,989 entries of 10 bytes: the largest table that fits in 2^20 bytes) is recomputed by the program for the new step cost and the memory budget 2^20; the success lower bound is 0.39000. The recovery circuit is 1532 operations (q = 0, no XOR with q).
Nothing else changed: the relation, the search, the handlers, the recovery (two passes), the ledger method and the experiments' form are those of 1cd0dd3b.

## Premises, and what was checked

H1 (score-critical, model premise, four clauses): success of the attempt on the fixed target is at least the success P_F of the same procedure against a uniformly random function; clause (d) is the lazy-sampling hazard for the program's adaptive choices. It cannot be tested at width 256 and is declared, not proved: an assumption, no proof is known. Lemma 2 proves P_F >= 0.390000001000 (exact certificate of Appendix A) for the random function with no premise besides H1. A hazard deficit eps is repaired by extra time: 0.0072 bit for eps = 0.01, 0.0370 bit for eps = 0.05, 0.0760 bit for eps = 0.10, 0.2075 bit for eps = 0.25. H3 (supporting, a declared machine convention): the 1856-register machine convention, the charges of the rolled program (moves, loop control, message slots), the 36-byte instruction charge, and the charge of the generator's code at 36 bytes per compiled instruction. Nothing else in the success bound is heuristic.
Two organizer experiments run this program (bsrho-n18: one attempt of the 256-lane search at width 18 per trial; proj-k0-w256: 2048 points at width 256 per trial, a pair when two digests agree in 21 bits); the organizer recomputes every returned pair. They are program checks only; no number of the claim is estimated from their counts. The program's own counts (`python3 bsrho.py --stats`, untrusted, descriptive): T3 n=18: attempts returning a verified pair: target 175 of 256, ideal function 182 of 256; T1 n=12 fresh K: 256 runs, mean first repeat 81.97 (sqrt(pi N/2) = 80.21). The experiments run in 4.5 s and 6.2 s for 256 trials each on the development machine (truncated widths as in a6ee439c).
Outside the shipped experiments, the program's scalar digest was compared with the organizer's reference `blake3(M, r)` at 3, 4 and 7 rounds (2000 random messages each), and at 7 rounds also with the `blake3` library (2,000 messages): no differences. The rolled bit-sliced step was compared with `blake3(M, 7)` on 8,192 messages and on 4,096 lanes chained for 7 steps, with the `blake3` library on 8,192 messages, the packed recovery circuit on 448 messages, and with the straight-line step of 1cd0dd3b on 16,384 lanes lane by lane: no differences. The selftest compares the step with the scalar compression on 4,096 lanes and on 4,096 lanes chained for 7 steps, runs the flat listing (with its loop control) in an interpreter against the compiled step, and prints 0 shared and 0 unused gates for the generator's networks.

## Generator memory

The program is generated at setup. Model (proof 3.6): the generator is a freestanding C program of 2,249 compiled instructions (80,964 bytes at 36 bytes each) with 34,716 bytes of scratch (10,056 nodes of the larger segment, an 8-bit use count and a 16-bit pin each), held in the region that the table and the register file occupy once the search runs (setup phase 944,908 bytes, search phase 1,048,510). Measured: the C program compiled to WebAssembly in a sandbox whose guest memory is capped at 16 pages = 1,048,576 bytes emits the identical program (instruction text equal line by line, q = 0) in 14,206,554 wasm operations, and as a static x86-64 binary without libc it does the same under `prlimit --as=1048576` (and under `--data`); its static arrays total 863,944 bytes including the final code region and the counters. The generator of the entry is that C program; the Python generator is only the reference whose output text it reproduces.

## Limits

- The full 256-bit functional graph, iterations beyond 2^40 and other keys were not tested; H1 is not proved.
- Memory is 1,048,510 bytes, 2^19.99991, under 2^20 (claimed as 20). The memory account is convention-heavy: the code is charged 36 bytes per instruction (inline immediate), the register file 1856 x 32 bytes, the generator's image and scratch overlay the table region at setup.
- The register file of 1856 is this entry's declaration (the program uses exactly that many); the profile fixes no register count, and smaller files are not priced for the rolled program.
- The loop-control and message-permutation charges are this entry's reading of the cost model (counted operations and instructions, no free decode, no free re-indexing); the machine of the model has no instruction set, so a judge may price a loop differently. A rolled program with a different permutation scheme (for example double-buffered slots in a two-round body) would have other counts; we did not build it.
- The memory budget 2^20 makes the table the largest that fits; the split of the memory between code, registers and table was not optimised over other program layouts (for example a rolled recovery circuit, or fewer registers by in-place half-round updates), which would enlarge the table by a few thousand entries, a gain of about 0.01 bit.
- The Python tooling (ledger, selftest, the reference checks, the organizer pipeline) was not run under a cap at the claimed memory: a Python interpreter is not the machine of the model. Only the circuit generator, which defines the program, q, the register count and the instruction count, was run under the caps stated above.
- The generator's code is charged by the number of WebAssembly instructions of the compiled C program (2,249), one instruction each; this count is a stated convention. Handler, key-scan and entry charges are stated upper bounds (proof 3.3); the generator is charged 200 operations per primitive call and per emitted line (14,206,554 wasm operations measured against 18,871,000 charged). Together they are below 1e-7 of the ledger.
- The Section 4 proof was checked by its author only; the judges' rating of the same Section 4 in 1cd0dd3b and a6ee439c is not yet known.
