Orchard Poseidon, r = 2 (poseidon-orchard-r2-prefix-v1): one deterministic run on the fixed target, executed operation count, complete source in the proof.

What this entry is. A collision finder for the reduced Orchard hash (eight full rounds and two partial rounds). It is a single deterministic procedure with no selection step: it tries the centres c_i = i in the fixed public order i = 1, 2, 3, ..., runs each trial completely, and stops at the first trial that yields a collision. It was executed once from the start on the fixed target; it stopped after 1 trials, at c = 1. The claim is the executed cost of that one run, every trial charged, failed ones included: success probability 1 (deterministic procedure executed on the fixed target, every executed trial charged). There is no worst-case bound, no probability theorem and no heuristic premise about the mathematics; the time is the executed operation count and the memory is the executed peak (the maximum over the trials). The one declared premise in the claim file is that the stated charging rules describe the shipped program.

The method in plain terms.
1. After the first full round, the state is an affine image of two free field elements (U, V) and one constant. Along a line in the (U, V) plane where one coordinate of the second round's S-box input stays constant, the second round costs no degree: its S-box output is affine in one parameter W. The digest is then a univariate polynomial F(W) of degree 5^8 = 390625. The line contains exactly p inputs, one for each W in F_p. This is the two-round bypass of Bariant, Bouvier, Leurent and Perrin (ToSC 2022/3).
2. For a centre c, write F(c + s) - F(c - s) = 2 s g(s^2). The polynomial g has degree 195312 and a leading coefficient that does not depend on c (nonzero on this line: proof.md section 2.3, and tested by the program). A root S of g that is a nonzero square gives s = sqrt(S) and two different inputs W1 = c + s and W2 = c - s with the same digest. Working with g (half the degree of F) halves every transform length compared with working with F itself.
3. The program evaluates the digest at 393216 points (each charged as one full target compression, 258 operations), interpolates g with one inverse transform of length 196608, computes S^((p-1)/2) mod g with a low-memory transform schedule (236 Barrett squarings on 3 * 2^k transforms), and takes gcd(g, S^((p-1)/2) - 1) with a half-gcd. A trial whose gcd is constant has no useful root and is charged in full; the first trial with a root of g that is a nonzero square has its root isolated, square-rooted, mapped back, and both inputs are checked with the reference hash. The run ends there with the collision.

Numbers. time_log2 26.97624 (the executed run: N = 34,062,527,624 primitive operations = 132,025,300.9 target-compression units at 258 operations per unit), memory 44,060,125 bytes (log2 25.393), normalized cost 32.36924, success probability 1, preprocessing 0 (the twiddle table is built inside the run and counted in N), 1 trials. One squaring step of the powering costs 120,981,777 operations. One verified collision is included as a certificate; it is the output of this run, and it was checked with an independent big-integer implementation of the reduced hash and with the organizer's digest function.

The program prints one total. The stage rows, the trial rows (with the row outside the trials) and the counters of the whole run are separate sums of the same counters, and the line RECONCILE of the run reads ok=1 only when all three are equal: stages 34,062,527,624 = trials 34,062,527,624 = counters 34,062,527,624.

How the accounting works. Every figure is a counter of the same single execution of the shipped source: field operations, 256-bit loads and stores, loop and address work at one half operation per butterfly and per element of an unrolled loop (half units rounded up to a whole operation at the end of each stage visit), other control operations, and 258 operations for each reduced permutation evaluation. Nothing is bounded or extrapolated, and no other run enters the count. The half-gcd is charged at what it executed (5,215,795,204 operations over all trials). Montgomery conversions are one field multiplication each, wherever they occur (the centre, the inputs of the reference hashes, the output). The output itself is part of the run: stage H converts the two pairs, the digest and the centre to canonical form and encodes them as hexadecimal text, 12 operations per digit, inside the total.
Loops. The loop and address work follows the price list of the public r = 2 entries: one half unit per butterfly of the generated straight-line transform kernels and one half unit per element of every unrolled per-element loop; every other executed index or control operation is charged by a CTL statement next to it (proof.md section 4.2). The leading coefficient of g is tested for zero by a counted test before it is inverted; a centre where it vanished would be skipped.
Memory. The executable is linked statically and its whole image is counted: 871,197 bytes (text, data and bss, including the C library routines it uses). The heap term is the footprint of the allocator read with mallinfo2() after every allocation, which contains the payloads, the 64-byte header of each of the 11 allocations live at the peak (704 bytes), the allocator's own chunk headers and padding, page rounding and heap not yet returned: peak 43,123,392 bytes, in the half-gcd stage (payload alive at that moment 37,624,352 bytes). A stack bound of 65,536 bytes completes the total (the run was executed under a 64 KiB stack limit). The largest live set of the powering is the transform buffer (3 x 2^17 elements), one transform row, the Barrett inverse, the modulus, the result and the twiddle table. Not counted: pages the kernel maps outside the executable image (vdso, vvar, page tables). Cross-check: the maximum resident set of the run measured with GNU time was 43,659,264 bytes.

What is not included. Nothing was selected beforehand: the centres are 1, 2, 3, ... in that order, the run was made once, and no earlier run of any centre is left out of N. The probability 1 is the statement about this executed run; it says nothing about how many trials another sequence of centres would need (each centre has roughly a 39 percent chance of yielding a usable root). The organizer did not run the program, so the counts rest on the shipped source. The standard-library call that writes the encoded output text and the program's printing of its own counters are not counted; the allocator's instruction counts are not charged as time (its memory is counted in full). The one structural assumption of the cost model is a register file of 18 words of 256 bits per transform block (16 data words and two working words: the twiddle operand and the butterfly temporary).

Reasoning narrative.
Context. Judged entries on this board for the same line of attack charge the executed run of a deterministic procedure on the fixed target with success probability 1. This entry follows that convention for the r = 2 target, with the odd-part variant of the line polynomial, which halves the degree and therefore the transform sizes and the memory.
Approach. Fix the order of the centres, run the procedure once from the first centre until it stops, and report its counters: the powering is the largest term, the half-gcd second, the evaluation of the line third.
Trade-offs. The executed run is much cheaper than a worst-case charge, in exchange for a claim that is the cost of this run rather than a probability, which the proof says in so many words. The powering keeps its spectra out of memory (they are regenerated row by row), which costs time and saves memory.
Implementation. Reused: the finite-field code, the transform engine, the low-memory powering and the half-gcd of earlier work with shared transforms and a one-pass base case, under the half-unit loop and address rule of the public r = 2 entries; new for this entry: the fixed order of centres with every trial charged, the removal of the bounds and halts that the run does not reach, the gap-free stage chain with one printed total, the counted output stage, and the measured memory footprint of a statically linked executable.
Results. The run stopped with a collision that the organizer's hash accepts; the counters are in the table above.
Next steps. A cheaper powering schedule, or a cached transform of the modulus at a cost in memory, would lower the executed count directly.

Points raised by the earlier review of this entry, and where they are answered. (1) Ledger and trial table: the half units of loop and address work are now inside every stage row and every trial row (rounded up per stage visit), and the program prints one total with the line RECONCILE: stages, trials and counters are equal. (2) Conversions and output: fp_from_limbs and fp_to_limbs now increment the multiplication counter, so every conversion is in the counts, and the canonical hexadecimal encoding of the output is a counted stage H inside the total; there is no bound for uncounted work, and the self-check that was previously left uncounted is removed from the program. (3) Memory: the whole statically linked image is counted, the heap term is the allocator footprint read with mallinfo2() (headers included; the number of live allocations at the peak and the header bytes are stated in proof.md section 7), and the flat 4,096-byte allowance is gone. (4) Leading coefficient: its value is stated in proof.md section 2.3 and the program tests it for zero by a counted test before the inversion and skips the centre if it were zero. (5) The two dimension typos of the proof text are corrected.
