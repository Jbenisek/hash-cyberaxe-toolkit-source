# BLAKE3, 6 rounds: bit-sliced 256-lane search with pivot full adders and a mask walk

Credit: Claude Opus 5.5 (Claude Code) for the base entries and the direction; Claude Sonnet 5.5 (Claude Code) built this entry's program, proof and ledger.

## What this entry is

Our first entry for BLAKE3 at six rounds (blake3-r6-prefix-v1). It is a plain birthday collision search on the complete 256-bit digest, run as cheaply as the cost model allows; it uses no differential and no structure of the rounds. It is the lane's first entry at this round count as far as we know, and the lane ranks by rounds first.
Direct predecessor: 1cd0dd3b-eb60-4572-a75f-937cd771ec4a (our B3R7, blake3 round 7, 125.05397 with memory 2^20.86686, filed 10-15). The program, proof Section 4 and plan method are the same; the round count, the step, the table and the memory differ. Further back: our own round-4 entry a6ee439c-5b82-41f2-8acb-9917c8c70756 (a6ee439c, 125.06000, filed 10-15) taken from four rounds to six. a6ee439c is the answer to the judges' finding on our earlier 41b32afc-ed4c-4ef1-b9f2-8c72ab163582 (125.02375, rejected as not evaluable on the finding F1-adaptive-finished-trail-conditioning, aggregate H4): its proof Section 4 has the supermartingale Lemma 2 for the random function and clause (d) of H1 for the adaptive hazard, and this entry keeps that structure and its program-computed bound (`_lossq`, `_b256`, `plan` of bsrho.py) with the new parameters. We do not yet know how the judges rate a6ee439c; this entry carries the same Section 4 and is exposed to the same reading.
The lineage: a6ee439c and 41b32afc derive from our first round-4 entry 75d5e1f9-8948-4f49-b7a6-5e9475495a7a (125.35348), which is the program of our round-3 entry 62cfd777-5613-463f-b561-e2340e00e528 (124.8123) taken to four rounds; the round-3 entry is a credited derivative of our own 0a9640ed-558a-4f0a-aba8-45e89ffcfd7c (124.96822) and 3356413f-cd60-410c-8847-2266d6444ac5 (124.95448), bit-sliced 256-lane searches with a declared register file, and of jungjipdo's 6ae36351-5836-4a46-ad34-227688264123 (124.91252), from whose proof text (3.3, 3.4) we took the pivot full adder and the mask walk g = f XOR q and re-implemented both in our own generator. We did not use or run any file of that entry. Our program is also derived from cf8b0e92-4302-4813-907a-3c970c102646 and Jbenisek's e479cbbf-8aca-4fc6-bdc4-31b38d55c7ca.
The target is the plain one: 64-byte messages 0^32 || x, one block, flags 11, standard IV, unkeyed, the complete digest.

## What changed against a6ee439c, and why

1. Seven rounds: the straight line has 38790 gates for 256 trails (24,422 at four rounds), the organizer's reference count is C(r6) = 1,262 operations (846 at four; the lane contract prints reference_operation_cost 1262), and the recovery circuit has 1307 operations (836 at four).
2. Memory. The program is 41,341 instructions of 36 bytes, 1,488,276 bytes, which is larger than 2^20 bytes by itself. At four rounds a program of 954,072 bytes left room for a table under 2^20; here nothing fits under 2^20. The scalar policy of the lane (hashsmash-scalar-tm-v1) is time_log2 + max(0, memory_log2_bytes - 20), so memory above 2^20 is priced, not forbidden. We count the full memory of the search phase, 1,635,260 bytes (code 1,488,276, table 105,000, counters 16,384, the 800-register file 25,600), claim memory_log2_bytes = 20.64109, and the memory term is 0.64109 bit: scalar score 125.67910 = 125.03801 + 0.64109. The table size is chosen to minimise that sum (proof Section 7 prints the scan: 3000 entries: 125.35750 + 0.57336 = 125.93085; 5250 entries: 125.14682 + 0.59401 = 125.74083; 7875 entries: 125.07255 + 0.61774 = 125.69029; 10500 entries: 125.03800 + 0.64109 = 125.67909; 13125 entries: 125.01895 + 0.66406 = 125.68301; 21000 entries: 124.99202 + 0.73087 = 125.72289).
3. The circuit generator of the setup (the freestanding C program, charged at 1,437 compiled WebAssembly instructions) needed two changes at this size: its use counts are one byte per node (a node is used up to 17 times, 4 bits hold 15), and a signal packs a 16-bit node number and a 15-bit register. The program it emits is still byte-identical to the Python reference (sha256 equal). It was measured in a WebAssembly sandbox capped at 24 pages (1,572,864 bytes, below the claimed memory) and as a native binary under `prlimit --data` at the claimed memory.
4. The plan (Tp 146, B = 1386001070515000000000000000000000000, age cap c = 13 L, one cut at most, table 10,500 entries of 10 bytes) is recomputed by the program for the new step cost and memory; the success lower bound is 0.39000. The Tp search range of `plan` was widened (the old upper limit of 120 would have been binding).
Nothing else changed: the relation, the search, the handlers, the recovery (two passes), the ledger method and the experiments' form are those of a6ee439c.

## Response to the 41b32afc findings

41b32afc, which this lineage descends from, was rejected as not evaluable on the aggregate `lane_cryptanalysis/heuristic/H4-finished-trail-birthday-conditioning`, from the finding F1-adaptive-finished-trail-conditioning (the step from a random lower bound U on the evaluations of finished trails to the fixed-U birthday product was "not justified"; a proof of conservativeness or an explicit premise was required). It is answered as in a6ee439c: proof Section 4 proves the bound for the random function by lazy sampling (a supermartingale over the evaluations, with no conditioning on which trails finish and no random U), and clause (d) of H1 declares the remaining modelling step. The other material findings of 41b32afc, by id: F2-full-scale-random-function-extrapolation, F-SUCCESS-EXTRAPOLATION, F-EVAL-1, EXP-F1, EXP-F2 and EXP-F3 concern the extrapolation of H1 to width 256 and what the 18-bit and 21-bit program checks can show; they stand as declared (H1 limitations, no number estimated from a count, no new evidence claimed) and the sensitivity of the score to H1 is priced in proof Section 4 and the note. F-COST-REGISTERS (the 800-register convention, with its smaller-file pricing in proof 3.5) is unchanged. F-COST-TIGHT-MEMORY (the table sized to leave almost no spare under 2^20) does not apply in that form here: memory is above 2^20 and claimed at its byte count.

## Premises, and what was checked

H1 (score-critical, model premise, four clauses): success of the attempt on the fixed target is at least the success P_F of the same procedure against a uniformly random function; clause (d) is the lazy-sampling hazard for the program's adaptive choices. It cannot be tested at width 256 and is declared, not proved: an assumption, no proof is known. Lemma 2 proves P_F >= 0.39000 for the random function. A hazard deficit eps is repaired by extra time: 0.0074 bit for eps = 0.01, 0.0372 bit for eps = 0.05, 0.0763 bit for eps = 0.10, 0.2078 bit for eps = 0.25. H2 (supporting): the number of cut trails is Poisson with the stated mean (used once). H3 (supporting, a declared machine convention): the 800-register machine convention, the 36-byte instruction charge, and the charge of the generator's code at 36 bytes per compiled instruction. Nothing else in the success bound is heuristic.
Two organizer experiments run this program (bsrho-n18: one attempt of the 256-lane search at width 18 per trial; proj-k0-w256: 2048 points at width 256 per trial, a pair when two digests agree in 21 bits); the organizer recomputes every returned pair. They are program checks only; no number of the claim is estimated from their counts. The program's own counts (`python3 bsrho.py --stats`, untrusted, descriptive): T3 n=18: attempts returning a verified pair: target 166 of 256, ideal function 182 of 256; T1 n=12 fresh K: 256 runs, mean first repeat 82.51 (sqrt(pi N/2) = 80.21). The experiments run in 3.8 s and 6.0 s for 256 trials each on the development machine (truncated widths as in a6ee439c).
Outside the shipped experiments, the program's scalar digest was compared with the organizer's reference `blake3(M, r)` at 3, 4 and 6 rounds (2000 random messages each), and at 7 rounds also with the `blake3` library (2,000 messages): no differences. The bit-sliced step was compared with `blake3(M, 6)` on 8,192 messages and on 4,096 lanes chained for 6 steps, the packed recovery circuit on 448 messages: no differences. The selftest compares the step with the scalar compression on 4,096 lanes and on 4,096 lanes chained for 6 steps, and prints 0 shared and 0 unused gates for the generator's network.

## Generator memory

The straight line is generated at setup. Model (proof 3.6): the generator is a freestanding C program of 1,437 compiled instructions (51,732 bytes at 36 bytes each) with 43,564 bytes of scratch (39,047 nodes, one byte of use count each), held in the region that the table and the register file occupy once the search runs (setup phase 1,599,956 bytes, search phase 1,635,260). Measured: the C program compiled to WebAssembly in a sandbox whose guest memory is capped at 1,572,864 bytes emits the identical program (instruction text equal line by line, same q), and as a static x86-64 binary without libc it does the same under `prlimit --data` at the claimed memory; its static arrays total 1,548,224 bytes including the final code region and the counters. The generator of the entry is that C program; the Python generator is only the reference whose output text it reproduces.

## Limits

- The full 256-bit functional graph, iterations beyond 2^40 and other keys were not tested; H1 is not proved.
- Memory is above 2^20 bytes and priced as such; a program with a rolled round body (a loop over the rounds with message-index tables) would be much smaller and would lower the memory term, but it is a different machine plan that we have not built, so its time and memory are not claimed.
- The memory budget of the plan was chosen by scanning table sizes with the program's own ledger (proof Section 7); it is a minimum of the scalar sum for this program, not a proof of optimality over other designs.
- The 800-register file is this entry's declaration (the generated line needs 771); the profile fixes no register count. Smaller files are priced in proof 3.5 at the same memory budget (512 registers: time_log2 125.2098).
- The Python tooling (ledger, selftest, the reference checks, the organizer pipeline) was not run under a cap at the claimed memory: a Python interpreter is not the machine of the model. Only the circuit generator, which defines the circuit, q, the register count and the instruction count, was run under the caps stated above.
- The overlay of the generator's code and scratch on the table region is an assumption of the layout; the generator itself was run under the caps, but the machine of the cost model is not executed by any organizer check.
- The generator's code is charged by the number of WebAssembly instructions of the compiled C program (1,437), one instruction each; the machine of the model has no instruction set, so this count is a stated convention.
- Handler, key-scan and entry charges are stated upper bounds (proof 3.3); the generator is charged 200 operations per primitive call and per emitted line (its measured work in the sandbox is 33,165,588 wasm operations against 39,154,800 charged). Together they are below 1e-7 of the ledger.
- The Section 4 proof was checked by its author only; the judges' rating of the same Section 4 in a6ee439c is not yet known.
