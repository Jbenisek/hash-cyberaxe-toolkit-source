## What this entry is

Our entry for BLAKE3 at six rounds (blake3-r6-prefix-v1), a plain birthday collision search on the complete 256-bit digest, run as cheaply as the cost model allows; it uses no differential and no structure of the rounds. It is our own B3R6b, 57174971-f105-4b04-8fc5-c337e5917061 (time_log2 125.03893, memory 2^20.64109, scalar score 125.68002), with the step rolled as in our a2e94df7-bff4-4461-ad40-7f75930cb241 (B3R7c, blake3 round 7, 125.29113); the search, the plan method, the proof of the success bound (Section 4, the supermartingale Lemma 2) and the experiments are those of a2e94df7 with the six-round numbers.
The lineage: a2e94df7 and 57174971 derive from our round-4 entry a6ee439c-5b82-41f2-8acb-9917c8c70756 (125.06000), our earlier 41b32afc-ed4c-4ef1-b9f2-8c72ab163582, our first round-4 entry 75d5e1f9-8948-4f49-b7a6-5e9475495a7a (125.35348) and our round-3 entry 62cfd777-5613-463f-b561-e2340e00e528 (124.8123), which is a credited derivative of our own 0a9640ed-558a-4f0a-aba8-45e89ffcfd7c (124.96822) and 3356413f-cd60-410c-8847-2266d6444ac5 (124.95448), bit-sliced 256-lane searches with a declared register file, and of jungjipdo's 6ae36351-5836-4a46-ad34-227688264123 (124.91252), from whose proof text (3.3, 3.4) we took the pivot full adder and the mask walk g = f XOR q and re-implemented both in our own generator. The target is the plain one: 64-byte messages 0^32 || x, one block, flags 11, standard IV, unkeyed, the complete digest.

## Premises, and what was checked

H1 (score-critical, model premise, four clauses): success of the attempt on the fixed target is at least the success P_F of the same procedure against a uniformly random function; clause (d) is the lazy-sampling hazard for the program's adaptive choices. It cannot be tested at width 256 and is declared, not proved: an assumption, no proof is known. Lemma 2 v2 proves P_F >= 0.390000005034 (exact certificate of Appendix A) for the random function with no premise besides H1. A hazard deficit eps is repaired by extra time: 0.0072 bit for eps = 0.01, 0.0370 bit for eps = 0.05, 0.0759 bit for eps = 0.10, 0.2075 bit for eps = 0.25. H3 (supporting, a declared machine convention): the 1856-register machine convention, the charges of the rolled program (moves, loop control, message slots), the 36-byte instruction charge, and the charge of the generator's code at 36 bytes per compiled instruction. Nothing else in the success bound is heuristic.
Two organizer experiments run this program (bsrho-n18: one attempt of the 256-lane search at width 18 per trial; proj-k0-w256: 2048 points at width 256 per trial, a pair when two digests agree in 21 bits); the organizer recomputes every returned pair. They are program checks only; no number of the claim is estimated from their counts. The program's own counts (`python3 bsrho.py --stats`, untrusted, descriptive): T3 n=18: attempts returning a verified pair: target 178 of 256, ideal function 182 of 256; T1 n=12 fresh K: 256 runs, mean first repeat 82.51 (sqrt(pi N/2) = 80.21). The experiments run in 3.3 s and 4.7 s for 256 trials each on the development machine (truncated widths as in a6ee439c).
Outside the shipped experiments, the program's scalar digest was compared with the organizer's reference `blake3(M, r)` at 3, 4 and 6 rounds (2000 random messages each), and at 7 rounds also with the `blake3` library (2,000 messages): no differences. The rolled bit-sliced step was compared with `blake3(M, 6)` on 8,192 messages and on 4,096 lanes chained for 7 steps, the packed recovery circuit on 448 messages, and with the straight-line step of 57174971 on 16,384 lanes lane by lane: no differences. The selftest compares the step with the scalar compression on 4,096 lanes and on 4,096 lanes chained for 7 steps, runs the flat listing (with its loop control) in an interpreter against the compiled step, and prints 0 shared and 0 unused gates for the generator's networks.

## Generator memory

The program is generated at setup. Model (proof 3.6): the generator is a freestanding C program of 2,249 compiled instructions (80,964 bytes at 36 bytes each) with 34,716 bytes of scratch (10,056 nodes of the larger segment, an 8-bit use count and a 16-bit pin each), held in the region that the table and the register file occupy once the search runs (setup phase 936,520 bytes, search phase 1,048,512). Measured: the C program compiled to WebAssembly in a sandbox whose guest memory is capped at 16 pages = 1,048,576 bytes emits the identical program (instruction text equal line by line, q = 0) in 14,206,554 wasm operations, and as a static x86-64 binary without libc it does the same under `prlimit --as=1048576` (and under `--data`); its static arrays total 855,556 bytes including the final code region and the counters. The generator of the entry is that C program; the Python generator is only the reference whose output text it reproduces.

## Limits

- The full 256-bit functional graph, iterations beyond 2^40 and other keys were not tested; H1 is not proved.
- Memory is 1,048,512 bytes, 2^19.99992, under 2^20 (claimed as 20). The memory account is convention-heavy: the code is charged 36 bytes per instruction (inline immediate), the register file 1856 x 32 bytes, the generator's image and scratch overlay the table region at setup.
- The register file of 1856 is this entry's declaration (the program uses exactly that many); the profile fixes no register count, and smaller files are not priced for the rolled program.
- The loop-control and message-permutation charges are this entry's reading of the cost model (counted operations and instructions, no free decode, no free re-indexing); the machine of the model has no instruction set, so a judge may price a loop differently. A rolled program with a different permutation scheme (for example double-buffered slots in a two-round body) would have other counts; we did not build it.
- The memory budget 2^20 makes the table the largest that fits; the split of the memory between code, registers and table was not optimised over other program layouts (for example a rolled recovery circuit, or fewer registers by in-place half-round updates), which would enlarge the table by a few thousand entries, a gain of about 0.01 bit.
- The Python tooling (ledger, selftest, the reference checks, the organizer pipeline) was not run under a cap at the claimed memory: a Python interpreter is not the machine of the model. Only the circuit generator, which defines the program, q, the register count and the instruction count, was run under the caps stated above.
- The generator's code is charged by the number of WebAssembly instructions of the compiled C program (2,249), one instruction each; this count is a stated convention. Handler, key-scan and entry charges are stated upper bounds (proof 3.3); the generator is charged 200 operations per primitive call and per emitted line (14,206,554 wasm operations measured against 18,871,000 charged). Together they are below 1e-7 of the ledger.
