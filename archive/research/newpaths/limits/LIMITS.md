# BLAKE3 field limits: what the reference code does at and past each limit (2026-10-08)

This is a list of concerns for the designers. It is not an attack and does not describe one. Source: public BLAKE3-team/BLAKE3 master (C version 1.8.7), with shallow copies of the named files in `src\`. Nothing was compiled or run. Every finding comes from reading the code. Levers: L = the v14 length difference (v14). C = the counter solved per trial (v12, v13).

## Per field
| Field | C (blake3.c, blake3_portable.c) | Rust (lib.rs, hazmat.rs, guts.rs) | What standard hashing produces |
|---|---|---|---|
| Chunk counter (v12, v13) | The public API cannot set it, because blake3.h has no offset setter. The internal `chunk_state_reset(.., uint64_t)` takes any value. The counter goes up by 1 per chunk with no overflow check. `count_so_far = counter*1024` wraps at 2^54 chunks. `cv_stack` is a fixed 55 x 32 B array and `hasher_push_cv` copies into it with no bounds check. UNCHECKED, but not reachable below 2^64 B. | `hazmat::set_input_offset(byte offset)` is VALIDATED by asserts: the hasher must be fresh and the offset a multiple of 1024. `update` asserts `max_subtree_len`, and `finalize`/`finalize_xof` assert offset 0. The docs say these "currently ... panic, but this is not guaranteed". Because the offset is in bytes, t <= 2^54-1 and v13 <= 2^22-1. `guts::ChunkState::new(u64)` is deprecated and doc-hidden but still pub, and it is UNCHECKED: any u64. | Design: t <= 2^54-1 (source comment: 2^54 chunks = 2^64 B). Our domain: t <= 2^51-1, v13 <= 2^19-1 (CONTEXTS) |
| Block length (v14) | `compress_pre(.., uint8_t block_len ..)` sets state[14] to 0..255 UNCHECKED. Bits 8..31 cannot be reached because of the type. | `platform::Platform::compress_in_place(block_len: u8)` is doc-hidden ("for benchmarks only") and UNCHECKED: 0..255. | 1..64. 0 only for the empty root message |
| Flags (v15) | `uint8_t`, UNCHECKED. Bits 8..31 cannot be reached. | `u8` through the platform API, UNCHECKED. The `hazmat::Mode` enum gives only the defined combinations. | Bits 0..6 only, in the combinations listed in CONTEXTS |
| Total input length | No length field exists. Length enters only through the counter and v14. Past 2^64 B there is no error and no clamp: the counter keeps counting and `count_so_far` wraps. The README states no limit. | `Hasher::count()` is u64 and `cv_stack` is `ArrayVec<55>`. Same design limit of 2^64 B. I found no runtime check in the parts I read. | <= 2^64-1 B (design) |
| XOF position (counter under ROOT) | `finalize_seek(seek u64)` sets the block counter to seek/64 <= 2^58-1. Whether seek+out_len goes past 2^64 is not checked. The counter keeps going rather than wrapping. | `set_position(any u64)` is unchecked. `io::Seek` CLAMPS to u64::MAX and returns an ERROR for a negative seek or a seek from the end. Reading past 2^64-1 B is DOCUMENTED as "unspecified". | ROOT with t <= 2^58-1 (v13 <= 2^26-1). Our digest is fixed at counter 0 (rows 1, 4, 11), so this is not a lever |

## Entry points that put values standard hashing never produces into the compression state
1. Raw compress: Rust `platform::Platform::compress_in_place`/`compress_xof` (doc-hidden pub) and C `blake3_compress_in_place`/`_xof` (internal header, non-static symbol). They accept any u64 counter, a block length of 65..255, flag bit 7, and undefined combinations such as PARENT|CHUNK_START. Feeds L (v14 > 64) and C (v13 >= 2^22, a free high word). Flags feed no lever because v15 is FIX.
2. `guts::ChunkState::new(t)` accepts any u64 counter, so it feeds C. Calling `finalize(false)` with no input gives an empty non-root chunk: v14 = 0, flags 3, counter t. Standard hashing never makes one, and hazmat refuses it ("empty subtrees are never valid"). Feeds L (v14 = 0 is outside 1..64) and C (same shape as row 9).
3. `guts::ChunkState::update` past 1024 B (DERIVED, not run). Only a `debug_assert` limits chunk size. `blocks_compressed` is a u8, so in a release build it wraps to 0 at block 257, and that block gets CHUNK_START again on a chained CV. A debug build panics instead. This breaks the CONTEXTS invariant "START is set exactly when CV = IV". It feeds neither lever directly. It is a row-12 (flags-shift) shape that real messages never make.
4. `guts` `finalize(is_root=true)` with t != 0. `root_hash` forces counter 0 and only checks this with a `debug_assert`. A multi-block chunk chained under counter t therefore ends in a ROOT block at counter 0. Hasher cannot produce this. It feeds C as a mixed state and is not a real digest.
5. `hazmat::set_input_offset` takes only legal values (t <= 2^54-1), but it computes a chunk at counter t without hashing the t KiB prefix. That makes it a cheap way to check v12/v13 trials. The real message still needs the prefix, so the price in CONTEXTS still applies.

## Concerns for the designers
- C lever: check every solved counter against our domain (v13 <= 2^19-1) and the design limit (v13 <= 2^22-1). A trial that uses a free high word, or a counter from the raw or guts entry points, counts a path that no message reaches.
- L lever: the difference set has 65 values (0..64), and 0 occurs only for the empty root message. A model that treats v14 as a free byte (u8 accepts 65..255) over-counts.
- Flags: undefined bit 7 and mixed combinations exist only at the raw compress level. v15 stays FIX in every real context.
- The verifier hashes a real message, so none of these values can reach it. These are checks that keep the model honest. They are not new paths.

Blocked: none. Not done: no entry point was built or run. The SIMD back ends were not read; I assumed they place v14 and v15 the same way the portable code does.
