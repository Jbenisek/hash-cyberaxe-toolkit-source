# B3Z6 code-size cut (shared solver code), blake3-r2 - 2026-10-15
**Verdict: OPEN-BUILD, conditional. Gain about 0.2-0.3 bit if the joint-solver code can be shared at <= 1.3x solver cost; hard ceiling 0.68 bit; break-even solver slowdown 2.03x at code = 50 MB. Not measured, ledger arithmetic only.**

1. What the 105.6 MB is. make_b3z6.py lines 72-75: 3,300,000 instr (bound) x 32 B = 105,600,000 B. The itemised count CODE_I = 3,296,384:
   - 28*2^9 = 14,336 (loop-body lane sites) + 2^17+2^7 = 131,200 (the ONE shared copy of an opened cluster already) + 10*2^9 = 5,120 (last batch): about 150,656 instr (4.8 MB). Already loop/shared code.
   - joint solver 2^21 = 2,097,152 instr (67.1 MB, 64%): "fewer than 2^14 labels of fewer than 2^7 instructions". Proof (9.4/regs paragraph, d190 candidate text): search written out statically per row and per prefix of free choices, every position/register named in the code, "no register is addressed by a value". This is generated per-node straight-line code, and the 2^14 x 2^7 is an upper-bound allowance, not a count.
   - context, routine, rest 2^20 = 1,048,576 instr (33.6 MB, 32%): also a bound (context = 39 lines straight-line, 90,917 units).
2. Smaller program. The batch/cluster code is already a loop plus one shared copy; only the solver (and the 2^20 rest) is big. Options: (a) subroutine shared across the six outcomes of S (tree shape is the same per outcome; only constants differ, and the descriptors already sit in registers): per node call+return+descriptor load roughly 3-6 units on a node of tens of units; (b) fully table-driven interpreter: needs register-indirect access, which the machine lacks -> every register access becomes load/store (+2-3 per op) and pattern 3 (no zero-cost decode) charges the decode: f about 2-3. Solver metered time is the CREDIT row: 7.683e20 = 24.3% of N (3.162e21), calls row 1.1e18. So time N' = N + CREDIT*(f-1). (Loop control: 3 units/iteration is included in f; no separate loop here.) Unmeasured: the real per-node cost, so f is a parameter.

A build would: rewrite the joint solver as one shared traversal routine parameterised by the outcome descriptor (a call per outcome, not code per outcome), re-count its units (CM(T) meter, CREDIT, CALL budget, m_C change), replace the 2^14 x 2^7 allowance and the 2^20 "rest" bound by exact instruction counts (the counts alone may drop the bound with f=1: exact counts are the cheapest first step; unknown, could be 0 gain if the bounds are tight), and keep the pattern-3 charge of every call/return. Risk: judge must accept a changed solver ledger; solver registers (63 of 64 used) leave no room for call state; that is untested.
