## Premises, and what was checked

H1 (score-critical, model premise, four clauses): success of the attempt on the fixed target is at least the success P_F of the same procedure against a uniformly random function; clause (d) is the lazy-sampling hazard for the program's adaptive choices. It cannot be tested at width 256 and is declared, not proved: an assumption, no proof is known. Lemma 2 v2 proves P_F >= {Pcert} (exact certificate of Appendix A) for the random function with no premise besides H1. A hazard deficit eps is repaired by extra time: {sens_short}. H3 (supporting, a declared machine convention): the {regs}-register machine convention, the charges of the rolled program (moves, loop control, message slots), the 36-byte instruction charge, and the charge of the generator's code at 36 bytes per compiled instruction. Nothing else in the success bound is heuristic.
Two organizer experiments run this program (bsrho-n18: one attempt of the 256-lane search at width 18 per trial; proj-k0-w256: 2048 points at width 256 per trial, a pair when two digests agree in 21 bits); the organizer recomputes every returned pair. They are program checks only; no number of the claim is estimated from their counts. The program's own counts (`python3 bsrho.py --stats`, untrusted, descriptive): {stats1}; {stats2}. The experiments run in {t18} s and {t21} s for 256 trials each on the development machine (truncated widths as in a6ee439c).
Outside the shipped experiments, the program's scalar digest was compared with the organizer's reference `blake3(M, r)` at 3, 4 and {Rn} rounds ({nchk} random messages each), and at 7 rounds also with the `blake3` library (2,000 messages): no differences. The rolled bit-sliced step was compared with `blake3(M, {Rn})` on 8,192 messages and on 4,096 lanes chained for 7 steps, the packed recovery circuit on 448 messages, and with the straight-line step of {pred8} on {nrolled} lanes lane by lane: no differences. The selftest compares the step with the scalar compression on 4,096 lanes and on 4,096 lanes chained for 7 steps, runs the flat listing (with its loop control) in an interpreter against the compiled step, and prints 0 shared and 0 unused gates for the generator's networks.

## Limits

- The full 256-bit functional graph, iterations beyond 2^40 and other keys were not tested; H1 is not proved.
- Memory is {mem} bytes, 2^{memlog2:.5f}, under 2^20 (claimed as 20). The memory account is convention-heavy: the code is charged 36 bytes per instruction (inline immediate), the register file {regs} x 32 bytes, the generator's image and scratch overlay the table region at setup.
- The register file of {regs} is this entry's declaration (the program uses exactly that many); the profile fixes no register count, and smaller files are not priced for the rolled program.
- The loop-control and message-permutation charges are this entry's reading of the cost model (counted operations and instructions, no free decode, no free re-indexing); the machine of the model has no instruction set, so a judge may price a loop differently. A rolled program with a different permutation scheme (for example double-buffered slots in a two-round body) would have other counts; we did not build it.
- The memory budget 2^20 makes the table the largest that fits; the split of the memory between code, registers and table was not optimised over other program layouts (for example a rolled recovery circuit, or fewer registers by in-place half-round updates), which would enlarge the table by a few thousand entries, a gain of about 0.01 bit.
- The Python tooling (ledger, selftest, the reference checks, the organizer pipeline) was not run under a cap at the claimed memory: a Python interpreter is not the machine of the model. Only the circuit generator, which defines the program, q, the register count and the instruction count, was run under the caps stated above.
- The generator's code is charged by the number of WebAssembly instructions of the compiled C program ({gencode}), one instruction each; this count is a stated convention. Handler, key-scan and entry charges are stated upper bounds (proof 3.3); the generator is charged 200 operations per primitive call and per emitted line ({genfuel} wasm operations measured against {genops} charged). Together they are below 1e-7 of the ledger.
