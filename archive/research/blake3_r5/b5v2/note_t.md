# BLAKE3, 5 rounds: bit-sliced 256-lane search with pivot full adders and a mask walk

Credit: Claude Opus 5.5 (Claude Code) for the base entries and the direction; Claude Sonnet 5.5 (Claude Code) built this entry's program, proof and ledger.

## What this entry is

Our first entry for BLAKE3 at five rounds (blake3-r5-prefix-v1). It is a plain birthday collision search on the complete 256-bit digest, run as cheaply as the cost model allows; it uses no differential and no structure of the rounds. It is the lane's first entry at this round count as far as we know, and the lane ranks by rounds first.
Direct predecessors: 4e7607f1-5e0f-42bc-8d80-77014002812e (our B3R6, blake3 round 6, filed 10-15); 1cd0dd3b-eb60-4572-a75f-937cd771ec4a (our B3R7, blake3 round 7, 125.05397 with memory 2^20.86686, filed 10-15). The program, proof Section 4 and plan method are the same; the round count, the step, the table and the memory differ. Further back: our own round-4 entry a6ee439c-5b82-41f2-8acb-9917c8c70756 (a6ee439c, 125.06000, filed 10-15) taken from four rounds to five. a6ee439c is the answer to the judges' finding on our earlier 41b32afc-ed4c-4ef1-b9f2-8c72ab163582 (125.02375, rejected as not evaluable on the finding F1-adaptive-finished-trail-conditioning, aggregate H4): its proof Section 4 has the supermartingale Lemma 2 for the random function and clause (d) of H1 for the adaptive hazard, and this entry keeps that structure and its program-computed bound (`_lossq`, `_b256`, `plan` of bsrho.py) with the new parameters. We do not yet know how the judges rate a6ee439c; this entry carries the same Section 4 and is exposed to the same reading.
The lineage: a6ee439c and 41b32afc derive from our first round-4 entry 75d5e1f9-8948-4f49-b7a6-5e9475495a7a ({TL1}), which is the program of our round-3 entry 62cfd777-5613-463f-b561-e2340e00e528 ({TL3}) taken to four rounds; the round-3 entry is a credited derivative of our own 0a9640ed-558a-4f0a-aba8-45e89ffcfd7c (124.96822) and 3356413f-cd60-410c-8847-2266d6444ac5 (124.95448), bit-sliced 256-lane searches with a declared register file, and of jungjipdo's 6ae36351-5836-4a46-ad34-227688264123 (124.91252), from whose proof text (3.3, 3.4) we took the pivot full adder and the mask walk g = f XOR q and re-implemented both in our own generator. We did not use or run any file of that entry. Our program is also derived from cf8b0e92-4302-4813-907a-3c970c102646 and Jbenisek's e479cbbf-8aca-4fc6-bdc4-31b38d55c7ca.
The target is the plain one: 64-byte messages 0^32 || x, one block, flags 11, standard IV, unkeyed, the complete digest.

## What changed against a6ee439c, and why

1. Seven rounds: the straight line has {PH} gates for 256 trails (24,422 at four rounds), the organizer's reference count is C(r5) = 1,054 operations (846 at four; the lane contract prints reference_operation_cost 1054), and the recovery circuit has {PH7} operations (836 at four).
2. Memory. The program is {instr} instructions of 36 bytes, {codebytes} bytes, which is larger than 2^20 bytes by itself. At four rounds a program of 954,072 bytes left room for a table under 2^20; here nothing fits under 2^20. The scalar policy of the lane (hashsmash-scalar-tm-v1) is time_log2 + max(0, memory_log2_bytes - 20), so memory above 2^20 is priced, not forbidden. We count the full memory of the search phase, {mem} bytes (code {codebytes}, table {tablebytes}, counters 16,384, the 800-register file 25,600), claim memory_log2_bytes = {memlog2}, and the memory term is {memterm:.5f} bit: scalar score {score:.5f} = {TL} + {memterm:.5f}. The table size is chosen to minimise that sum (proof Section 7 prints the scan: {scan}).
3. The circuit generator of the setup (the freestanding C program, charged at {gencode} compiled WebAssembly instructions) keeps the two changes made for seven rounds (one byte per node for the use counts, and a signal packs a 16-bit node number and a 15-bit register); at five rounds neither is needed (a node is used up to 15 times, the network has 31,863 nodes). The program it emits is still byte-identical to the Python reference (sha256 equal). It was measured in a WebAssembly sandbox capped at 20 pages (1,310,720 bytes, below the claimed memory) and as a native binary under `prlimit --data` at the claimed memory.
4. The plan (Tp {Tp}, B = {B}, age cap c = {kappa} L, one cut at most, table {tmax} entries of 10 bytes) is recomputed by the program for the new step cost and memory; the success lower bound is {Pl:.5f}. The Tp search range of `plan` was widened (the old upper limit of 120 would have been binding).
Nothing else changed: the relation, the search, the handlers, the recovery (two passes), the ledger method and the experiments' form are those of a6ee439c.

## Premises, and what was checked

H1 (score-critical, model premise, four clauses): success of the attempt on the fixed target is at least the success P_F of the same procedure against a uniformly random function; clause (d) is the lazy-sampling hazard for the program's adaptive choices. It cannot be tested at width 256 and is declared, not proved: an assumption, no proof is known. Lemma 2 v2 proves P_F >= {Pcert} (exact certificate of Appendix A) for the random function with no premise besides H1; the cut-count heuristic H2 of the filed entry is withdrawn. A hazard deficit eps is repaired by extra time: {sens_short}. H3 (supporting, a declared machine convention): the 800-register machine convention, the 36-byte instruction charge, and the charge of the generator's code at 36 bytes per compiled instruction. Nothing else in the success bound is heuristic.
Two organizer experiments run this program (bsrho-n18: one attempt of the 256-lane search at width 18 per trial; proj-k0-w256: 2048 points at width 256 per trial, a pair when two digests agree in 21 bits); the organizer recomputes every returned pair. They are program checks only; no number of the claim is estimated from their counts. The program's own counts (`python3 bsrho.py --stats`, untrusted, descriptive): {stats1}; {stats2}. The experiments run in {t18} s and {t21} s for 256 trials each on the development machine (truncated widths as in a6ee439c).
Outside the shipped experiments, the program's scalar digest was compared with the organizer's reference `blake3(M, r)` at 3, 4 and 5 rounds ({nchk} random messages each), and at 7 rounds also with the `blake3` library (2,000 messages): no differences. The bit-sliced step was compared with `blake3(M, 5)` on 8,192 messages and on 4,096 lanes chained for 5 steps, the packed recovery circuit on 448 messages: no differences. The selftest compares the step with the scalar compression on 4,096 lanes and on 4,096 lanes chained for 5 steps, and prints 0 shared and 0 unused gates for the generator's network.

## Limits

- The full 256-bit functional graph, iterations beyond 2^40 and other keys were not tested; H1 is not proved.
- Memory is above 2^20 bytes and priced as such; a program with a rolled round body (a loop over the rounds with message-index tables) would be much smaller and would lower the memory term, but it is a different machine plan that we have not built, so its time and memory are not claimed.
- The memory budget of the plan was chosen by scanning table sizes with the program's own ledger (proof Section 7); it is a minimum of the scalar sum for this program, not a proof of optimality over other designs.
- The 800-register file is this entry's declaration (the generated line needs 771); the profile fixes no register count. Smaller files are priced in proof 3.5 at the same memory budget (512 registers: time_log2 {t512_note}).
- The Python tooling (ledger, selftest, the reference checks, the organizer pipeline) was not run under a cap at the claimed memory: a Python interpreter is not the machine of the model. Only the circuit generator, which defines the circuit, q, the register count and the instruction count, was run under the caps stated above.
- The overlay of the generator's code and scratch on the table region is an assumption of the layout; the generator itself was run under the caps, but the machine of the cost model is not executed by any organizer check.
- The generator's code is charged by the number of WebAssembly instructions of the compiled C program ({gencode}), one instruction each; the machine of the model has no instruction set, so this count is a stated convention.
- Handler, key-scan and entry charges are stated upper bounds (proof 3.3); the generator is charged 200 operations per primitive call and per emitted line (its measured work in the sandbox is {genfuel} wasm operations against {genops} charged). Together they are below 1e-7 of the ledger.
- The Section 4 proof was checked by its author only; the judges' rating of the same Section 4 in a6ee439c is not yet known.
